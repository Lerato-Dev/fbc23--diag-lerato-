1. Purpose and scope

The Mini Task Tracker lets one person keep a list of tasks with a title, an optional description and a due date, and mark each task as Pending or Completed. It is a two-part web application: a Next.js front end that runs in the browser and an Express API that stores tasks in a SQLite database file.

It was built for the FBC23 Developer Diagnostic Brief. The goal is a small application that runs end to end, is structured cleanly, and can be explained step by step.

In scope

  • Create, view, edit, complete and delete tasks.
  • Filter the list by status (All, Pending, Completed).
  • Validate every request on the server and return clear error messages.
  • Store tasks so they survive a restart of the API.
  • A layout that works on a phone and on a desktop.

Deliberately out of scope

  • Sign-in, user accounts and per-user task lists (listed as "Should have, as time allows" in the brief).
  • Sorting options, search, pagination, deployment. See section 11.

2. Users and roles

There is one role. Anyone who can open the front end, or send a request to the API, can do everything.

RoleWhoAllowed to
Task owner (anonymous)A single person running the app on their own machineList, filter, view, create, edit, complete and delete any task

Because there is no sign-in, the API never returns 401 or 403. Those branches are drawn as "not applicable" in the request flow in section 7.

3. Functional requirements

Each requirement is written so it can be tested. API requirements can be checked with Postman or PowerShell; UI requirements in the browser.

3.1 API

IDRequirement
FR-1POST /api/tasks with a valid body creates a task and returns 201 with the saved task, including its new id and timestamps.
FR-2A title is required, is trimmed, and must be 1 to 120 characters after trimming. Otherwise the API returns 400.
FR-3A description is optional, is trimmed, defaults to an empty string, and must be 2000 characters or fewer.
FR-4A due date is required and must match the format YYYY-MM-DD.
FR-5Status must be Pending or Completed. When it is left out, it defaults to Pending.
FR-6GET /api/tasks returns 200 with all tasks, ordered by due date (earliest first), then by newest id first.
FR-7GET /api/tasks?status=Pending or ?status=Completed returns only tasks with that status. Any other value returns 400.
FR-8GET /api/tasks/:id returns 200 with the task, or 404 when no task has that id.
FR-9PUT /api/tasks/:id replaces the title, description, due date and status of an existing task, sets updated_at, and returns 200 with the updated task. It returns 404 when the task does not exist.
FR-10PATCH /api/tasks/:id/complete sets the status to Completed and returns 200. Completing an already completed task also returns 200.
FR-11DELETE /api/tasks/:id removes the task permanently and returns 200 with a confirmation message, or 404 when it does not exist.
FR-12Any :id that is not a positive whole number (for example abc, 0, -3, 1.5) returns 400 before the database is touched.
FR-13A body that fails validation returns 400 with an errors array, one entry per problem, each naming the field and a readable message.
FR-14A body that is not valid JSON returns 400. A body larger than 100 KB returns 413.
FR-15A request to a path that does not exist returns 404 with the message "API endpoint not found."
FR-16An unexpected server error returns 500 with a generic message. The full error is written to the API terminal, never sent to the client.
FR-17GET / returns 200 with a message saying the API is running (health check).
FR-18Tasks are stored in api/database/tasks.db. The folder and table are created automatically on first start, and tasks remain after the API restarts.

3.2 User interface

IDRequirement
FR-19On load, the page shows "Loading tasks..." until the list arrives, then shows every task with its title, status badge, description (if any) and due date in the browser's local date format.
FR-20The header shows the total number of tasks ("1 task" or "N tasks").
FR-21The "Add a task" form has Title (required, max 120), Description (optional, max 2000) and Due date (required, date picker). Submitting creates the task and clears the form.
FR-22While a save is in progress, the submit button is disabled and reads "Saving..." so it cannot be clicked twice.
FR-23Clicking Edit fills the form with that task, changes the heading to "Edit task", shows a "Cancel edit" button and scrolls to the form. Saving keeps the task's current status.
FR-24A Complete button appears only on Pending tasks. Completed tasks show their title struck through.
FR-25Clicking Delete asks "Are you sure you want to delete this task?" and deletes only if the user confirms.
FR-26The All / Pending / Completed buttons filter the list. The active filter is highlighted and marked with aria-pressed.
FR-27When the list is empty, the page says "No tasks found" and suggests adding a task, or names the empty filter ("There are no completed tasks.").
FR-28After every create, update, complete or delete, a success message appears and the list reloads from the API. When a request fails, the API's message (or field messages joined together) appears in a red alert.

6. API design

Base URL: http://localhost:5000 (from PORT in api/.env). All bodies are JSON. Every response uses the same envelope:

{
  "success": true | false,
  "message": "Human-readable result",        // most responses
  "data":    { ...task } | [ ...tasks ],     // on success, when there is data
  "errors":  [ { "field": "title", "message": "Title is required" } ]  // 400 validation only
}

Request body for POST and PUT

{
  "title": "Prepare diagnostic walkthrough",   // required, 1-120 chars
  "description": "Explain the architecture",   // optional, max 2000
  "dueDate": "2026-11-28",                     // required, YYYY-MM-DD
  "status": "Pending"                          // optional, defaults to Pending
}

8. Architecture and structure

The system is two separate programs on two ports. The browser loads the front end from port 3000 and calls the API on port 5000 directly. Because the ports differ, they are different origins, which is why the API needs CORS.

How this maps to MVC: routes and controllers are the Controller, the service and model are the Model, and the JSON response (plus the React page) is the View. The fit is imperfect: a REST API has no real view, and "model" is split into a service for rules and a model file that acts as a repository for storage.

Dependency injection: not used. taskModel.ts imports the database connection directly and the service imports the model directly. This keeps the code short but means the service cannot be tested without a real database. See item G-6.

9. Decisions and trade-offs

D-1 Database: SQLite (Architecture Decision Record)

ContextOne user, one table of short text records, run locally by reviewers who should not need to install a database server.
OptionsSQLite (file), PostgreSQL (server), MongoDB (document store).
CriteriaZero setup on a clean machine; data is structured with a fixed shape; constraints enforced by the database; low write volume.
DecisionSQLite through better-sqlite3. It is relational, enforces CHECK constraints, needs no server, and the file is created automatically.
ConsequencesOnly one writer at a time, so it does not suit many simultaneous users. better-sqlite3 is a native module and must compile or download a binary for the installed Node version. Moving to PostgreSQL later means changing config/database.ts and taskModel.ts only.
Would change ifMany users write at once, the app is deployed to several servers, or reporting across many related tables is needed (PostgreSQL). MongoDB would only fit if task shapes became highly variable, which is not expected.

10. Assumptions and open questions

Assumptions

  • A-1 One person uses the app at a time, on their own machine.
  • A-2 Due dates in the past are allowed (for recording overdue work).
  • A-3 Lists stay small (under about 1,000 tasks), so no pagination is needed.
  • A-4 Deleting is permanent; there is no undo or archive.
  • A-5 The performance targets in NFR-5 are reasonable for a local SQLite app but have not been measured.

Questions for the team

IDQuestionCurrent behaviour
Q-1Should impossible dates such as 2026-02-31 be rejected?Accepted: the regex checks the format only
Q-2Should status be required on PUT, so leaving it out does not silently reopen a completed task?Missing status defaults to Pending. The UI always sends it
Q-3Should a completed task be reopenable from the UI?Only through the API (PUT)
Q-4Should DELETE return 204 No Content, as the Week 2 guide suggests?Returns 200 with a message
Q-5Should POST return a Location header pointing at the new task?No header
Q-6Should responses use camelCase to match request bodies?Requests use dueDate; responses use due_date
Q-7Should timestamps include a time zone (ISO 8601 with Z)?UTC without a zone marker
Q-8Is sign-in expected in the next iteration? It would change every endpoint (401/403) and the data model.No authentication

11. Out of scope and cut list

Will not build in this iteration

  • Sign-in, accounts and per-user task lists.
  • Search, custom sorting, pagination, tags or priorities.
  • Deployment to Azure, and Terraform (parked for Week 2).
  • Swagger / OpenAPI documentation (the empty swagger.ts and its packages should be removed or finished).

Cut first if time runs short (half-time test)

  1. The Edit feature (users can delete and recreate a task).
  2. The status filter.
  3. The delete confirmation dialog.

The thin vertical slice that must always work is: add a task, see it in the list, mark it complete, delete it.
